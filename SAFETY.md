# Clinical safety

## Status

**Experimental. Not for clinical use.** The engine calculates UK-WHO SDS and centiles and matches the Python engine bit for bit on the conformance corpus, but has had no clinical review (`R35`), no hazard log entries (`R27`), and no regulatory determination (`Q11`).

## What this software does

Calculates SDS, centiles, centile bands, and chart coordinates for children's growth measurements against published growth references, given a measurement, a date of birth, an observation date, a sex, and a gestation at birth.

## What it does not do

- It does not diagnose. A growth chart is one input to a clinical assessment, not a conclusion.
- It does not replace clinical judgement, examination, or confirmatory evidence.
- It does not validate that the growth reference chosen is clinically appropriate for the child. Choosing a syndrome-specific reference requires a documented diagnosis, and that judgement belongs to the clinician and the implementing system.
- It does not decide when a measurement is implausible beyond its declared SDS limits.

## Intended users and environment

Software engineers integrating growth calculations into clinical systems, researchers, and AI agents acting for them through the CLI or MCP server. Not intended for direct use by clinicians, patients, or families; those users are served by products built on top of it.

## Regulatory position

OpenGrowth is an independent Open Health Technology Foundation project. It is **not** a component of the RCPCH Digital Growth Charts platform and is **not** covered by that platform's MHRA registration or clinical safety file.

OpenGrowth is not registered as a medical device. Its regulatory position, including whether OHTF or the deploying organisation acts as manufacturer for any hosted service, must be settled before any clinical use. This is `Q11`.

Organisations deploying software built on this engine assume their own responsibilities under DCB0160, and under DCB0129 and UK MDR where they place a product on the market.

## Main safety evidence

The primary evidence that OpenGrowth calculates correctly is the same evidence used for the Python engine, applied to Rust:

- **Independent R vectors.** Around 4,000 fictional children generated by Tim Cole's R implementation, with SDS values computed independently of any RCPCH code. The Python engine is accepted against these at 1e-3 absolute SDS, a tolerance agreed with the statistician because interpolation implementations always differ slightly. OpenGrowth must meet the same gate.
- **Differential goldens from the Python engine.** Outputs captured from a pinned `rcpchgrowth` version across the existing fixtures and the coverage gaps listed in `spec/standard.md` section 8.2, compared at much tighter tolerances.

The R vectors catch errors shared by both RCPCH and OpenGrowth code. The Python goldens catch small drift and string, shape, and rounding differences the R vectors do not test. Neither is sufficient alone. See `spec/standard.md` sections 5 and 8.

## Hazards specific to this project

Reimplementing a clinical calculation engine in another language introduces hazards that the original does not have. Each needs an entry in the hazard log before any clinical use (`R21`).

- **Silent numerical divergence.** Rust may differ from Python in the last bits because of different normal-distribution implementations, different rounding, or different floating-point operation ordering. A small divergence in SDS could cross a centile-band boundary and change the words a clinician reads. Controls: declared tolerances, the R vectors and Python goldens above, and individual enumeration of every rounding-boundary difference rather than a blanket allowance.
- **Reference-data transcription error.** A table converted incorrectly would produce confidently wrong results across every affected age. Controls: per-table integrity tests covering point counts, ordering, and endpoint values, plus provenance recorded for every table.
- **Wrong or corrupted user-supplied reference data.** If UK90 tables are supplied at install time (`Q1`), a user could load a wrong version, a truncated file, or data from another source. Controls: import accepts only data matching a checked-in checksum manifest, the engine refuses to calculate against an unverified table, and provenance reports which data version was used.
- **Reference-selection divergence.** Age-based selection between reference components, and the rules for gestational correction, differ per reference and are the most intricate part of the engine. Preterm and early-infant assessment is where UK-WHO and WHO diverge most, which makes it the first place to look rather than the only place at risk. Controls: exhaustive boundary testing, and UK-WHO implemented last and gated hardest.
- **Correcting a defect without noticing it is clinical.** Some current Python behaviour is wrong but affects output. Correcting it during a port would be an undocumented clinical change. Control: the Category 1/2/3 defect policy in `spec/standard.md` section 6, which requires clinical sign-off before any Category 2 correction.
- **Divergence from the upstream engine over time.** If RCPCH changes `rcpchgrowth`, or stops maintaining it, the two implementations may disagree and integrators may not know which is right. Controls: goldens pinned to a named Python version, provenance that identifies the engine, and the upstream tracking policy in `Q10`.
- **Agent misuse through the CLI or MCP server.** An agent could call the engine with guessed inputs, such as assumed gestation or sex, and present the result as authoritative. Controls: the CLI and MCP surfaces require sex and gestation explicitly rather than defaulting them (the HTTP API keeps its existing defaults for compatibility), results carry provenance, and tool descriptions state the clinical-use boundary.

## Change control

- A change altering any clinical output updates this file and the safety documentation in the same change, or states why no update is needed.
- Reference-data changes record source, licence, transformation, and validation evidence.
- Tests defending safety-relevant behaviour cite the hazard or clinical source they protect.
- Preterm and early-infant logic requires clinical review, not only passing tests.

## Reporting a safety concern

Open an issue labelled `hazard` in this repository and notify the Clinical Safety Officer. If the concern is also a security vulnerability, report it privately as described in [SECURITY.md](SECURITY.md) instead.
